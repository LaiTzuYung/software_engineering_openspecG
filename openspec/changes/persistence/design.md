# Design

## Context

參見 proposal.md 的 Why。活動目前由 `ActivityManager` 持有單一可變 `ActivityState`；提交的驗證、重複檢查、取號與 Map 更新集中在同步 `submitAnswers`，Socket handler 在其返回後推播。學生 session map 位於 HTTP server 閉包，Socket 透過 resolver 查詢。題目集 repository 與試算表原值備份各自使用 `data/` JSON。回寫及還原 preview service 的預覽識別碼則是記憶體狀態。

## Goals / Non-Goals

**Goals:**

- 以單一版本化快照檔恢復活動、題目集副本、所有接受提交、下一序號及學生身份。
- 讓每個可觀察的活動狀態更新在成功持久化後才推播，並確保存檔按序完成。
- 安全忽略無效快照、保留原始損壞檔並保持伺服器可啟動。
- 以第二個 server instance 共用暫存資料目錄驗證真正的程序狀態重建。

**Non-Goals:**

- 不保存線上 Socket 數、排名結果、成功組結果或回寫預覽快照。
- 不支援多活動歷史；新活動會取代唯一目前活動。
- 不改變 D4 提交排序語意或現有 restore-first 備份格式與還原流程。

## Decisions

### 將活動及學生工作階段序列化為一份快照

在 `data/` 使用一個明確命名的活動 JSON，根物件含 schema version、活動本體及 sessionToken 對組別識別。Activity 內含活動代碼、階段、組別、排名規則、題目敘述開關、題目集完整深複本、提交陣列及下一序號。提交記錄保存組別、題號、全活動序號、伺服器 ISO 時間及小題答案。Map 於 JSON 以陣列或明確物件編碼，載入時重建為 Map；不保存衍生排名、成功組或線上頁數。

建立新活動時同一檔案被新快照取代，符合本系統只同時支援一個活動的既有決定。題目集副本由建立活動當下的 Activity.questionSet 保存，之後不從 repository 查找該活動資料。

**替代方案：**各狀態分檔或另存結果索引。多檔會引入跨檔一致性；結果索引則與提交重算的單一真相衝突，因此採單一快照。

### 以驗證、暫存檔替換及串行佇列保證快照完整性

持久化邊界負責 schema/version 與必要欄位、關聯及不變量驗證。保存先寫同目錄唯一暫存檔，完成後 rename/replace 正式檔；失敗清理暫存檔但不得破壞舊正式檔。啟動讀取任何解析錯誤、版本不支援或格式錯誤時記錄錯誤、保留正式檔並讓 Manager 保持空狀態，不自動覆寫該檔。後續明確建立的新活動才可用有效快照取代它。

所有快照寫入經同一非拒絕佇列依提交順序串行化，序列化當下的狀態快照（不可延遲到佇列執行時才讀取可變 Activity）。狀態操作保存完成前不推播或回成功。每個持久化呼叫者處理自身錯誤；佇列必須在前一筆失敗後仍能繼續，避免永久拒絕或舊快照覆蓋新狀態。

**替代方案：**同步阻塞寫檔簡單但會阻塞事件迴圈；同時啟動非序列化 async write 會允許較舊寫入最後完成。採有序快照佇列，在記憶體原子區段之後執行非同步存檔。

### 保留 D4 同步原子區段，將提交存檔與推播安排在其後

提交路徑仍完整呼叫既有同步驗證與記憶體提交函式，函式內不加入 await、回呼或存檔 I/O，故實際伺服器收到順序仍決定序號與重複勝出者。成功返回後立即建立不可變持久化快照並排入序列佇列；該提交的 Socket 更新與成功 acknowledgement 必須等到其快照寫完。由於後續請求可先完成同步提交，所有排入快照須各自代表排入時的完整狀態，且依序寫入；推播採用已完成提交快照所對應的狀態投影，避免先完成較新的保存卻廣播舊狀態。

階段、規則、敘述顯示、建立活動及新增學生身份亦按「同步更新模型／身份 → 擷取快照 → await 有序保存 → 推播／成功回覆」安排。持久化失敗不得推播該次變更或回覆成功，須回報錯誤並確保記憶體狀態不會形成與磁碟永久分歧；實作需以變更前快照回復，或在失敗時採一致的伺服器錯誤策略。提交此處要特別定義錯誤處理，避免重新開放同組同題導致序號洞或已接受資料被回報失敗。

**替代方案：**先保存再執行提交同步驗證會讓 I/O 影響 D4 的接收先後，且無法保存待提交結果；不可採用。同步原子區段先完成，快照只在其後排隊。

### 從同一快照恢復 session，PIN 不進入活動資料

啟動時校驗完整快照後一次建立 ActivityState 與 session map；Socket 既有 resolver 直接從恢復的 map 找 token。學生頁保持既有 sessionStorage 欄位並在 Socket 重新連線取得快照視圖；視圖由恢復活動生成，故本組已送出狀態和答案自動重建。Socket online count 由新程序的連線集合計算，自然從 0 開始。

教師 PIN 不屬活動資料。若環境設定 `TEACHER_PIN`，啟動使用該固定值；否則照既有規則每次程序啟動生成新的隨機值。老師頁使用 sessionStorage PIN 自動打開或重連老師視圖，401 時清除無效 PIN 並顯示登入頁。題目集匯入檔與 `data/spreadsheet-export-backups/` 不移動、不清理。

**替代方案：**將 PIN 一同持久化會使未設定 PIN 時無法在每次啟動更新，也不符老師重新登入行為，因此 PIN 排除在活動快照外。

### 回寫備份持續沿用 restore-first，預覽不持久化

活動結束後，原值仍由既有 restore-first JSON 備份取得；持久化活動恢復後以相同 activityCode 查詢，無需改動備份模型。回寫與還原 preview 快照、preview ID 不寫入任何檔案，重啟後服務自然不認得舊 ID。老師畫面說明重啟後需重新按「回寫預覽」或「還原預覽」。

### 單一活動與題目集歷史語意

本專案現有 Manager 僅容納單一活動，因此 D12 的「保留所有活動」在此部署範圍意指保留目前唯一活動；新活動建立時以新快照取代舊活動檔。此明確差異記錄於本設計，不能實作成活動歷史清單。

## Risks / Trade-offs

- [每次提交都重寫完整快照，題目集或提交量增加時 I/O 成本提高] → 活動規模上限小且本機 JSON 易檢視；先採單檔原子快照，透過序列佇列避免併發寫壞。
- [檔案格式驗證不完整可能恢復不一致 Map 或錯誤序號] → 嚴格驗證 enum、組別/題目關聯、唯一提交鍵與序號唯一性、時間及答案欄位，拒絕整份快照而不部分載入。
- [程序在記憶體接受提交後、快照 rename 前立即被強制終止，最後提交仍可能未落盤] → 先保存再推播限制可避免向頁面確認未保存結果；一般 Ctrl+C 關閉需等待佇列完成。硬性斷電或強制終止的原子 rename 前窗口仍屬檔案系統持久性限制。
- [寫檔失敗時記憶體已變更] → 所有對外成功與推播等待存檔；實作須為每類狀態明確定義回滾或安全錯誤處置，並以測試證明失敗狀態不被推播。
- [sessionToken 以明文存在本機活動檔] → 僅限本機資料目錄且其已在 `.gitignore`；不輸出 token 至 log，沿用隨機 UUID token。

## Migration Plan

- 舊版本沒有活動快照時，以空活動啟動，不需遷移。
- 初次新建活動時建立版本化活動 JSON；舊題目集 JSON 與既有回寫備份不轉換。
- 升級後遇到無效快照不刪除、不覆寫，伺服器以空活動提供管理介面；使用者可保留檔案供檢查，另建新活動後才產生有效快照。
- 回退版本時舊程式仍不使用此快照；需保留該檔以供再次升級恢復，不自動清理。
