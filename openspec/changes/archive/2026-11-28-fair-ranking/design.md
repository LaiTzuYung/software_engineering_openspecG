# Design

## Context

參照 proposal.md 的動機與 `specs/live-buzzer/spec.md`、`specs/result-export/spec.md` 的驗收契約。現有 `AcceptedSubmission.sequence` 是全活動唯一遞增序號，提交以題目分組保存；`getQuestionRanks` 計算每題原始順位，`getQuestionResults` 目前選每題第一筆。老師 view、CSV 與回寫都消費現有結果介面。學生 view 在搶答前隔離他組資料，結果只於活動結束提供。

## Goals / Non-Goals

**Goals:**

- 將規則選擇、鎖定、中央純函式結果重算及各消費端整合列為一致的技術邊界。
- 以提交序號保證跨題處理順序確定，並保留原始順位供稽核與匯出。
- 使用同一個重算結果提供老師檢視、結束後學生卡片、CSV 和回寫預覽。

**Non-Goals:**

- 不新增結果儲存、資料庫、事件日誌或外部相依套件；活動目前僅存於伺服器記憶體。
- 不改答案驗證、提交接受順序、題組答案輸入方式或學生搶答中隔離原則。

## Decisions

### 1. 活動狀態只保存規則，不保存計算結果

在活動狀態加入排名規則，建立時預設 `speed`，並以統一的規則更新入口檢查階段；HTTP 與 Socket 控制器都呼叫同一入口。只有 `preparing` 接受更新。其他階段回傳明確中文訊息「搶答開始後不能更改排名規則」。

選擇只保存規則、由提交資料重算，符合現有 process-local 活動模型，也避免答案變動後快照過時。另存結果或每次提交增量更新會造成需維護多份狀態，且更難保證重算一致。

### 2. 建立一個純函式計算完整排名結果

在提交領域加入純函式，以活動的題目集、組別、規則及所有已接受提交產生不可變結果。先由既有 `getQuestionRanks` 取得各題原始順位；再將所有題目提交攤平，依全活動 `sequence` 遞增排序。均分上限以 `Math.ceil(questionSet.questions.length / groups.length)` 計算。依序追蹤各組成功題數、每題是否已有成功組，以及每筆的最終順位：跳過不佔最終順位；其他提交依該題順序編號。題組只有一筆活動提交，因此只計一題。

結果需同時含逐筆提交資訊（題號、組別、原始與最終順位、是否成功、說明、跳過狀態）與逐題資訊（成功組、成功答案、原因）。速度規則也經同一輸出型別產生，順位照舊，讓下游不必另走舊判定。每題全部被跳過時，原因依該題提交組別及其活動顯示順序組合；跳過提交本身的說明使用該組的指定句，遞補成功提交的說明使用其之前該題被跳過組名。

選擇完整排序重算而非逐題計算，因規則明確跨題共享組成功數。重用原始順位函式，避免複製其題內排序規則。全活動序號唯一，排序無需客戶端時間或額外平手規則。

### 3. 各輸出端只能讀取中央計算結果

老師 view 將逐筆結果映射至題目×組別格，並於結果列呈現排名規則、跳過/遞補文字、成功標示及整題原因。學生 view 一律只包含排名規則及原有允許資料；`stage !== ended` 時 results 維持 `null` 且不可序列化任何逐筆排名欄位，結束後只映射每題成功組、答案與可顯示的無成功組原因。

CSV 以中央結果填入原始順位、最終順位、成功及說明欄；跳過列的最終順位為空字串。回寫沿用中央逐題成功答案。移除 CSV 和回寫對成功組的獨立推導，避免各端偏離核心演算法。

### 4. 規則設定 API 與畫面共享相同規則呈現

建立活動請求可附排名規則；缺值或合法預設為純速度。新增老師規則更新 HTTP/Socket 路徑（若既有介面有兩種控制管道，兩者共用同一領域更新函式）。老師 view 在準備中提供切換、顯示均分 cap；開始後顯示唯讀字串。學生狀態僅帶可公開的規則 ID/顯示文字與 cap，不帶任何提交計算結果。規則說明字串集中格式化，確保老師、學生顯示「均分上限（每組最多成功 N 題）」一致。

## Risks / Trade-offs

- [均分上限重算需排序全部已接受提交] → 活動規模目前是單機課堂規模；使用一次排序 `O(S log S)`，S 為已接受提交數，且不在每個答案內複製或保存結果。
- [老師與學生序列化若共用過寬結果物件，可能洩漏排名] → 分別採明確白名單映射；學生搶答中不建立或回傳結果欄位，並以 HTTP、Socket 與畫面測試覆蓋。
- [舊的活動建立請求與狀態快照沒有排名欄位] → 建立入口將缺值視為純速度；活動不持久化，重啟後本就重建，不需資料遷移。
- [規則文案在多個輸出端被手動拼接會產生字差] → 將名稱、說明、跳過、遞補、整題原因格式集中於可測試格式化函式，模板只傳入組名與 cap。

## Migration Plan

1. 先加入純函式結果計算及針對決策單 2-15 的單元測試，維持預設純速度結果與既有行為。
2. 加入活動規則欄位、準備中設定 API 與搶答後拒絕更新，整合老師與學生視圖。
3. 將老師表格、學生結束結果、CSV、回寫改接中央結果，補齊自動測試。
4. 依 tasks.md 的 T2 人工測試確認四組、上限 1 的完整畫面流程。若需回退，移除規則選擇並將活動預設固定為純速度；提交資料格式無需轉換。
